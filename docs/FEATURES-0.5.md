# 0.5.0: prompt maker, Teams and Confluence prompts, scheduled sweeps, sync health, info buttons

Audience: people who use Claude Code with the Outlook, Teams, Confluence and Jira connectors. Claude does the reading; Jaffloop stores, shows and (new) schedules. No AI and no connectors inside the app.
Contract for the parallel workers. Already written (do not change their meaning): `src/shared/types.ts` (Settings.shareOneOnOneNotes, PromptArg, CustomPrompt, CustomPromptInput, SyncHealth, Schedule),
`src/shared/api.ts` (customPrompts, saveCustomPrompt, approveCustomPrompt, deleteCustomPrompt, syncHealth, schedules, saveSchedule, removeSchedule), `src/shared/prompts.ts` (new prompts teams-sweep, confluence-mentions, make-prompt; `schedulable` flag),
`src/renderer/components/info.tsx` (`<Info text label />`, the (i) hover/focus tooltip, CSS `.info-*` in styles.css). Do not edit another worker's files.

## A. Core + MCP (worker "core")
Files: `src/core/**`, `src/mcp/server.ts`, `src/shared/prompt-validate.ts` (new, pure), core/MCP tests.
* Migration `v6-custom-prompts`: table `custom_prompts(id TEXT PRIMARY KEY, title TEXT NOT NULL, description TEXT NOT NULL DEFAULT '', needs TEXT NOT NULL DEFAULT '[]', arguments TEXT NOT NULL DEFAULT '[]', text TEXT NOT NULL, approved BOOLEAN NOT NULL DEFAULT 0, source TEXT NOT NULL DEFAULT 'app', created_at DATETIME NOT NULL, updated_at DATETIME NOT NULL)`; fresh schema == migrated schema, registered in grdb_migrations; exportJSON includes `custom_prompts`.
* `src/shared/prompt-validate.ts`: `validateCustomPrompt(input: CustomPromptInput, builtinIds: string[]): string | null` (error text or null). Rules: id matches /^[a-z0-9][a-z0-9-]{1,39}$/ and is not a built-in id; title 1-80 chars; description ≤ 300; text 20-8000 chars; needs ≤ 8 entries of ≤ 40 chars; ≤ 8 arguments, each name /^[a-z][a-z0-9_]{0,29}$/ and unique, description ≤ 200, default ≤ 200; every {{placeholder}} in the text is a declared argument (and declared arguments that are required must appear in the text is NOT required). Used by the store, MCP and the renderer.
* Store: `customPrompts(): CustomPrompt[]` (by title), `customPrompt(id)`, `saveCustomPrompt(input, source: 'app'|'mcp', now): { prompt?: CustomPrompt; error?: string }` (validates with the built-in ids from `PROMPTS`; 'app' => approved=true; 'mcp' => approved=false, and editing an existing prompt via 'mcp' resets approved to false; keeps createdAt on update),
  `approveCustomPrompt(id, now)`, `deleteCustomPrompt(id)`, `syncHealth(now): SyncHealth` (rows per distinct non-null `source_label` over all items incl. proposed/done/dropped: total, last7Days by created_at, lastAt = max created_at; sorted by lastAt desc; `lastClaudeWriteAt` = latest `mcp_audit` row with wrote = 1).
* Settings: `reviewClaudeItems` default becomes TRUE (when no stored value; existing tests that assumed false must be updated), new `shareOneOnOneNotes` default TRUE. When `shareOneOnOneNotes` is false, MCP `get_person` and `prep_brief` leave the `notes` key out of `recent_interactions` (log_interaction still writes notes).
* MCP: new tools `list_prompts` (no args; returns { builtin: [{id,title}], custom: [{id,title,approved}] } so Claude avoids clashes) and `save_prompt` { id, title, description, text, needs[], arguments[{name,description,required,default}] } (read-only mode blocks it; validation errors are tool errors; result `{ id, status: "needs_approval", message: "Open Jaffloop, Settings, Claude (MCP) and approve it." }`; audit `save_prompt: <id>` wrote=true). `save_prompt` cannot approve or delete.
  `prompts/list` returns the built-ins plus APPROVED custom prompts (same shape); `prompts/get` serves approved custom prompts with `renderPrompt` semantics (build a JaffloopPrompt from the row); unapproved/unknown => -32602. Advertise `prompts: { listChanged: true }` and, while running over stdio, poll `store.dataVersion()` once a second and send `notifications/prompts/list_changed` when the set of approved custom prompts changed (keep it simple; unit-test the change detection function, not timing).
* Tests: `test/custom-prompts.test.ts` (validation rules, store round trip, approval rules, MCP save_prompt/list_prompts/prompts list+get incl. unapproved hidden, read-only), `test/sync-health.test.ts`, extend `test/compat.test.ts` (v6), `test/mcp.test.ts` (tool count 16), `test/mcp-prompts.test.ts` (14 built-in prompts), proposed/settings tests for the new default and `shareOneOnOneNotes`.

## B. Main process (worker "main")
Files: `src/main/**` (ipc.ts, new schedule.ts, main.ts), `src/shared/schedule.ts` (new, pure), tests `test/schedule.test.ts`, `test/main-*.test.ts`.
* ipc handlers for every new api method, same patterns as the existing ones (`data-changed` broadcast after writes): `customPrompts` / `saveCustomPrompt` (store.saveCustomPrompt(input,'app',now)) / `approveCustomPrompt` / `deleteCustomPrompt` / `syncHealth` call the Store methods the core worker is writing (signatures above; code against them, they appear while you work); `schedules` / `saveSchedule` / `removeSchedule` call `src/main/schedule.ts`.
* `src/shared/schedule.ts` (pure, importable by the renderer): `sweepCommand(promptText: string, extraAllowedTools = ''): string` returns one shell line: `claude -p '<promptText with single quotes escaped>' --allowedTools 'mcp__jaffloop__*' <each extra pattern quoted>` (extra patterns split on whitespace/commas, each must match /^[A-Za-z0-9_*.:-]+$/ else dropped);
  `scheduleLabel(promptId)` = `com.jafforge.jaffloop.sweep.<promptId>`; `buildPlist(s: Schedule & { command: string }): string` (launchd plist: Label, ProgramArguments ['/bin/zsh','-lc', command], StartCalendarInterval entries (one per weekday, or a single {Hour,Minute} when every day), StandardOutPath/StandardErrorPath = logPath, RunAtLoad false, plus a custom key `JaffloopSchedule` holding the JSON of {promptId,args,hour,minute,weekdays,extraAllowedTools}); `parsePlistJson(json: unknown): Schedule | null`.
* `src/main/schedule.ts`: `list()`, `save(s)`, `remove(promptId)` with injectable deps (fs dir, `exec` for `plutil -convert json -o - <file>` and `launchctl`), plist dir `~/Library/LaunchAgents`, files named `<label>.plist`, log path `~/Library/Logs/Jaffloop/sweep-<promptId>.log` (create the dir). save: validate hour 0-23, minute 0-59, weekdays 0-6, the prompt exists (built-in with `schedulable`, or an APPROVED custom prompt: look it up through the store), render the prompt text with `renderPrompt(p, args)` (required arguments must be present), write the plist, `launchctl bootout gui/<uid>/<label>` (ignore failure), `launchctl bootstrap gui/<uid> <plist>`; return `{ error }` text on any failure. remove: bootout + delete the file. Non-darwin: `{ error: 'Scheduling is only available on macOS.' }`. Never run launchctl in tests (inject).
* `mcpCommand` shown to users becomes `claude mcp add --scope user jaffloop -- "<binary>"` (and the dev variant keeps its `-e ELECTRON_RUN_AS_NODE=1` after the scope flag); update every test that asserts the command.
* Tests as above plus an ipc test for the new handlers if the existing ipc tests have a pattern.

## C. UI: info buttons everywhere (worker "info")
Files: all of `src/renderer/**` EXCEPT the Claude (MCP) tab (`windows/claude-prompts.tsx`, anything under `windows/claude-tab/`, and the Claude tab block of `windows/settings.tsx`, which worker "claude" owns). New `src/renderer/help.ts` (registry `HELP: Record<string, string>` id -> text, so wording lives in one place) and tests `test/ui-help.test.ts`, `test/e2e/features-info.test.ts`.
Requirement from the owner: "every action or tool has an info button explaining what it does when hovered". Rubric: put `<Info text=... label=... />` (from `components/info.tsx`) next to every control whose effect is not obvious from its label: every icon-only button, every toolbar/header action (Today controls, Ledger/People sort and layout, Review actions, Copy status), every item action (row actions menu, drawer actions: snooze, assign, remind, recur, tags, pin, nudge), triage keys in Inbox, proposal Accept / Dismiss / all, 1:1 mode (Start, Log, End and log, meeting notes, captured list, cancel), cadence strip and rings, person page actions and the edit sheet fields, onboarding form fields, the capture window and tray popover controls, the person brief and morning brief windows, the update panel, and every row in Settings tabs General, Notifications, Data and About (hotkey, theme, appearance, accent, density, sounds, quiet hours, export, reveal database, check for updates...). Plain obvious buttons (Cancel, Close, Done in a dialog) do not need one. Text: one or two plain sentences in the user's words ("Moves the item to tomorrow 9:00. Keyboard: s."), never a restatement of the label.
Placement: next to the label for rows and fields; for icon-only buttons put the explanation in the button's own `title`/aria-label AND wrap it with Info only when there is room (sidebar and dense rows: use `title` + aria-label, that counts); keep layouts from shifting (Info is inline-flex 17 px). Do not break existing tests or keyboard flows (Info buttons must not take focus in the j/k item list: use tabindex -1 inside lists and rows).
Tests: `ui-help.test.ts` asserts every HELP entry is non-empty, ≤ 220 chars and has no duplicates of its label; `features-info.test.ts` visits each main page and settings tab, checks the number of `[data-testid=info]` per screen is above a floor you set from the audit, hovers three of them and checks the tooltip text and that it disappears on mouse leave and Escape.
